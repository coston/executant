Check in this priority order, and act on the first one that applies:

1. **Prompting/task-definition quality** — does the narrative *explicitly* record real friction on any step: a judge FAIL entry, a self-healing fix entry, or a step marked failed? Only these count as friction. A step the narrative describes as passing clean on the first attempt (e.g. "no quality-control events — passed clean on the first attempt") has NO friction, full stop — do not read ambiguity, missing detail, or hypothetical edge cases into its prompt wording and call that "friction." If real friction exists, your suggestion MUST be about that step: name it and describe the specific gap the narrative revealed (what the feedback said was missing, or what the fix had to patch). This takes priority over any structural observation below, even if one is also true. If no step has recorded friction, skip to check 2.
2. Otherwise (every step passed clean on the first attempt), does any `forEach`/`repeat` step lack a `concurrency:` field? `repeat` supports the same `concurrency: N` field as `forEach` — check both. This is a purely mechanical, structural check: check only whether the field is present in the YAML. Do not reason about whether the step's task "should" run sequentially (e.g. flakiness testing, ordered dependencies, retry semantics) as a reason to withhold the suggestion — that judgment is out of scope here. This check applies to the `forEach`/`repeat` step itself, independent of whatever its child steps are — a `forEach` step whose child is already `type: script` (or has a `command` field, no API cost) still needs its own `concurrency:` field checked separately; "the child is already a script step" answers check 3 below, it is not a reason to skip or dismiss check 2. Do not invent other reasons to withhold the suggestion either — a `forEach` sourced from a shell command (e.g. `ls`, `find`) whose item count isn't visible in the YAML is not evidence of a "single-item" or "pass-through" case; the source expression's runtime output is unknowable at review time and is never grounds to skip this check. Check first whether the field is already set — if it is, do not suggest adding one or describe it as running sequentially. If a step genuinely lacks it, your suggestion MUST name the field `concurrency` explicitly (not "parallelize" or "run faster") — and if this check applies, it overrides any temptation to fall through to check 6 and conclude no change is needed.
3. Otherwise, is there a step whose `prompt` field is doing work deterministic enough to become a `command` (`type: script`, no API cost)? Apply this even when the workflow has only one step — a lone step is just as eligible as one among many. A prompt like "Run `<command>` and report whether it passed or failed" is exactly this case: no analysis or judgment is needed, only running a command and relaying its exit status, so it should become a script step. Check what the step actually has first: a step with a `command` field (and no `prompt`) is already a script step with zero API cost, even without an explicit `type: script` — do not claim it needs converting.
4. Otherwise, is there a repeated block of steps that could be factored into a `type: workflow` child?
5. Otherwise, consider the remaining executant features: `self_healing: true`, `llm_as_judge: true`, `allowed_tools:`, `context:`, `continue_on_error: true`. Only suggest from this list and the fields named above — do not invent unsupported YAML fields.
6. If nothing above applies — every step passed clean, every `forEach`/`repeat` step already has (or has no need to be checked for, per check 2's own scope) a `concurrency:` field, and the structure is already sound — say so plainly instead of inventing a suggestion. Reach this conclusion only after confirming checks 1–5 each genuinely do not apply; never use it to talk yourself out of a concurrency suggestion that check 2 already identified.

Before you decide how to phrase the suggestion, judge whether this task file reads as a **reusable template** — invoked with different `vars:`, referenced as a nested `type: workflow` module, or written in generic/parameterized language for use across different repos or runs — versus a **one-off task** tailored to this single run. For a reusable template, keep the suggestion general and prompt-focused (state the gap in terms any invocation would hit, not a value specific to this run). For a one-off task, you may reference concrete specifics from this run (exact file/step names, exact commands) since the file won't be reused elsewhere.

Decide on your single best answer before you start writing. Do not think out loud, do not show alternative candidates, and do not second-guess or revise your answer in the output — reason silently and commit to one conclusion.
